Problem and solution

The business problem

A service business often needs more than a name and email before it can assess a potential project. A static form can collect contact details, but it does not guide the visitor, ask structured discovery questions, verify contact information, or prepare a useful handoff for the business.

This project turned that first-contact experience into a guided AI consultation. The assistant could greet visitors, understand whether they wanted information or a consultation, collect project details through a structured intake flow, verify email ownership, and send the completed consultation summary to the business.

The key design choice was to keep the LLM and the business workflow separate. The LLM classified intent and handled flexible language, while deterministic backend logic controlled state, form stages, validation, video selection, email confirmation, and final lead submission.

The project was completed and deployed during September–December 2024. The public portfolio shows the architecture, workflow, and demo. A cleaned private backend package can be shared for code review without exposing secrets, production logs, client-facing assets, or deployment configuration.

System architecture

The system was built as a full-stack agentic web application with a FastAPI backend, LangChain/OpenAI intent layer, deterministic state management, async email verification, structured JSON logs, a Nuxt/Vue frontend, pre-scripted Elai.io-generated videos synchronized to assistant states, and production deployment on a DigitalOcean Droplet.

FastAPI backend

Served the assistant endpoint, handled session/thread IDs, received user messages, coordinated state, returned assistant text, and returned the video key associated with the current conversation state.

LangChain + GPT intent layer

Classified messages into intents such as greeting, consultation, services, information, thanks, goodbye, and unknown while tolerating natural language variation and typos.

Deterministic state machine

Maintained per-thread conversation state, form stage, collected details, finalization status, and last-active timestamps for cleanup.

Elai.io video response layer

Pre-scripted avatar/video clips were generated with Elai.io and mapped to conversation states, giving the assistant a polished visual response surface without requiring real-time video generation.

Email verification system

Generated secure numeric confirmation codes, sent them by SMTP, validated user email ownership, and only finalized submissions after successful verification.

Nuxt 3 / Vue frontend

Provided the chat interface and synchronized video player, connecting the user experience to backend assistant state and video-response keys.

Why this counts as agentic

This was not an open-ended autonomous agent. It was a bounded business agent: conversational at the surface, but controlled by deterministic workflow rules underneath.

Goal-directed workflow

The assistant was not only answering questions. It had a defined operational goal: move a qualified visitor through consultation intake and hand the result to the business.

Stateful progression

Each thread carried state across turns, including the current form stage, collected details, finalization status, and email verification progress.

Tool-like actions

The backend triggered workflow actions such as sending confirmation codes, validating verification input, selecting video responses, and submitting the lead summary.

Deterministic guardrails

The LLM classified intent and handled natural language, but the backend controlled what could happen next. This kept the business process stable and auditable.

Positioning: “agentic” here means a bounded, stateful workflow agent for a real business process. It does not mean unrestricted autonomy or unsupervised decision-making.

Core conversation flow

The application worked as a stateful consultation funnel: natural chat at the surface, deterministic workflow control underneath, and video clips triggered by the current assistant state.

1. User greeting / initial message: the assistant greets the visitor, classifies intent, and determines whether the user wants service information, a consultation, or general help.
2. Intent classification: the LLM classifies the message into supported intents such as greeting, consultation, info, services, goodbye, thanks, or unknown.
3. State update: the backend updates the user's thread state, including dialog state, form stage, collected user details, last-active time, and finalization status.
4. Elai.io video selection: the backend maps the current state to a video key. The frontend uses that key to display the corresponding pre-rendered Elai.io video clip.
5. Guided consultation form: if the user wants a consultation, the assistant collects structured business requirements through a known sequence of form stages.
6. Email confirmation: the user provides an email address, receives a confirmation code, and must enter the code before the lead can be finalized.
7. Business handoff: after verification, the backend emails the completed consultation details to the business. If the lead email fails, the consultation is not silently finalized.

Consultation form engine

The consultation flow collected structured information needed to qualify an AI solution request. The LLM provided conversational flexibility while the state machine kept the form deterministic.

Key technical highlights

Stateful agent design

Each conversation maintained a separate thread state, allowing the assistant to continue form collection and route responses based on prior progress.

Intent routing

The LLM was used to classify what the user wanted, but the backend controlled what the application did next. That separation kept the business workflow stable.

Deterministic form progression

The consultation process followed a known sequence with validation, cancellation support, edge-case handling, and finalization rules.

Elai.io-enhanced UX

Pre-rendered Elai.io video clips were mapped to assistant states, giving the site a more polished consultant experience without needing real-time avatar generation.

Email verification

Secure numeric confirmation codes helped prevent unverified form submissions and created a cleaner lead handoff process.

Hosted deployment

The project was deployed on a DigitalOcean Droplet, demonstrating a working hosted backend rather than only a local prototype.

Structured logs

The backend logged conversation activity and internal system events in JSON, improving observability and debugging for a multi-turn assistant workflow.

Configurable runtime boundary

Deployment-specific settings, API keys, session secrets, and email credentials were handled outside the source code.

Security, validation, and operational behaviour

Input validation

The form flow validated structured inputs such as email and confirmation code before finalizing the consultation submission.

Thread cleanup

Inactive conversation threads were cleaned after a timeout, preventing abandoned sessions from accumulating indefinitely.

Safer confirmation codes

The cleaned core logic uses cryptographically secure random digits for email confirmation codes rather than a general-purpose pseudo-random generator.

Lead finalization safety

Business lead submission is treated as part of finalization. If the lead email fails, the assistant does not silently claim that the consultation was submitted.

Security headers and CORS

The backend includes security headers and configurable frontend origins, with development defaults separated from production configuration.
